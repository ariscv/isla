# `start_multi` fork 即时并行改造计划

## 目标

针对 `executor::start_multi` 的多线程执行模型做内部重构，提升 fork 发生后的实际 CPU 利用率，使新产生的执行路径尽可能在 fork 当下立即并行执行，而不是延后进入外部调度循环再执行。

## 用户要求

1. `start_multi` 和 `start_single` 的对外接口必须保持不变。
2. 内部函数、内部调用方式、内部调度结构可以重构。
3. 在遇到 fork 时，应立即尝试并行执行新任务，而不是先放入队列等待后续调度。
4. 不采用当前这类“外部统一调度 + worker 睡眠/唤醒/偷取”的设计来实现立即并行。
5. 不希望保留复杂的 worker 池模型；线程在完成工作后可以直接结束，不需要长期驻留等待信号。
6. `start_single` 尽量少改，仍与 `start_multi` 复用同一个 `run_loop`。
7. `start_multi` 中的新线程创建应发生在执行线程遇到 fork 的位置，而不是依赖外部运行时阻塞等待某种信号后再创建。

## 现状判断

1. 当前 fork 真正产生活的地方在 `run_loop(...)` 内部，具体是符号 `Jump` 和 `Monomorphize` 两处分叉逻辑。
2. 当前 fork 后调用的是本地 `queue.push(Task { ... })`，这决定了新任务先进入队列，而不是直接获得独立执行单元。
3. 因此，如果不改 fork 点，仅修改 `start_multi(...)` 外层循环，最多只能改进“任务被其他线程拿到的速度”，不能实现“fork 即时并行”。

## 计划方案

### 方案总述

将当前“worker 池 + 外部调度”的模型改为“fork 点内联 spawn + 超限回退到共享待处理队列”的模型。

### 心智模型

可以把改造后的 `start_multi(...)` 想成一个“路径裂变器”，而不是“线程池调度器”。

1. 每个执行中的 OS 线程，只负责推进自己手上的当前 path。
2. 当当前 path 遇到 fork：
   - 如果系统还有线程名额，就在 fork 当下直接裂变出一个新线程去跑 child path；
   - 如果线程名额已经用满，就把 child path 暂存到一个共享待处理队列。
3. 这个共享队列不是 worker 池，也不是中央调度器，它只是“线程满了以后暂存任务的公共盒子”。
4. 线程不是常驻 worker：
   - 它不会空闲睡眠等待 `Poke`；
   - 也不会常驻循环等待新的外部信号；
   - 它在结束自己当前 task 后，只负责释放线程名额，并尝试一次性从共享队列里批量补出新的线程；
   - 然后自己直接退出。
5. 因此整个系统里，任何一个 task 在任意时刻只会处于三种状态之一：
   - 正在某个线程上运行
   - 暂存在共享队列中
   - 已经完成并交给 collector

这套模型的关键直觉是：

- 并发不是“等外面有人调度你”，而是“fork 的线程自己决定是否立刻把 child path 送上 CPU”。
- 线程不是“工人池中的工人”，而是“某条 path 的临时承载者”。
- 共享队列不是为了复杂化系统，而是为了在线程数达到上限时不丢任务、不阻塞 fork。

### 线程生命周期

以下是 multi 模式下单个 OS 线程从创建到退出的完整生命周期。

1. 创建前
   - `start_multi(...)` 进入 `thread::scope(...)`。
   - 创建共享运行时状态：
     - 线程上限 `limit`
     - 活跃线程计数 `active_threads`
     - 用于超限回退的共享待处理队列
     - collector 与执行所需共享上下文
   - 初始 `tasks` 也会走和 fork child task 相同的提交路径，避免“初始任务”和“fork 任务”出现两套不同调度语义。

2. 线程出生
   - 某个 task 被提交时，如果发现 `active_threads < limit`，则通过原子操作抢占一个线程名额。
   - 抢到名额后，立即在当前 `scope` 中 `spawn` 一个新线程。
   - 新线程创建后立刻开始执行该 task，不等待外部唤醒，不等待主线程调度。

3. 线程运行当前 task
   - 线程进入执行函数，重建 solver/checkpoint，对当前 task 调用 `run(...)` / `run_loop(...)`。
   - 线程此时只关心自己手上的当前 path，不负责扫描其他线程状态，也不等待外部事件。

4. 在线程内部遇到 fork
   - `run_loop(...)` 在符号 `Jump` 或 `Monomorphize` 处分裂出 child task。
   - 当前线程直接调用统一的 `submit(task)`：
     - 如果还有线程名额，当前线程立刻创建一个新线程去跑 child task；
     - 如果没有线程名额，当前线程把 child task 推入共享待处理队列。
   - 然后当前线程继续推进 parent path，不在 fork 点阻塞等待 child 完成。

5. 当前 task 完成
   - 线程完成一次 `run(...)` 后，立即调用 collector 处理结果。
   - collector 完成后，该线程不会变成“空闲 worker”，而是只做两个收尾动作：
     - 先释放自己占用的线程名额；
     - 再尝试成为本轮唯一的“补线程执行者”，统一从共享待处理队列中按当前可用名额批量补出新的线程。

6. 完成后的去向
   - 如果共享待处理队列中有任务且当前有空闲线程名额：
     - 抢到“补线程执行权”的当前线程负责把这一批任务按剩余名额直接批量 `spawn` 出去；
     - 自己不复用为 worker，不继续串行接着跑。
   - 如果共享待处理队列为空，或者已经没有可补的线程名额：
     - 当前线程直接退出；
     - 不进入阻塞等待，不保留驻留状态。

7. 线程退出后的系统行为
   - 即使某个线程退出，系统仍然可能还有其他线程在跑。
   - 如果其他运行中的线程后续又遇到 fork，那么它们仍可再次触发新的 `spawn`。
   - 也就是说，线程集合是动态变化的，不是一次性建好后固定不变的池子。

### 运行时流程图

可以把 `start_multi(...)` 想成下面这条链路：

```text
initial tasks / fork child task
        |
        v
    submit(task)
        |
        +-- active_threads < limit --> 立即 scope.spawn 新线程执行
        |
        `-- active_threads >= limit --> 放入共享队列

线程执行 task
        |
        v
遇到 fork ------> 再次 submit(child task)
        |
        v
task 完成
        |
        +-- 释放线程名额
        |
        +-- 抢到补线程执行权
        |       |
        |       +-- 共享队列非空且还有线程名额 --> 批量 spawn 若干新线程
        |       |
        |       `-- 无任务或无名额 --> 不补线程
        |
        `-- 当前线程退出
```

这里没有以下行为：

- 没有外部协调线程定期轮询后再发信号
- 没有 idle worker 阻塞等待 `recv()`
- 没有 `Poke` / `Kill` / `Idle` 之类的线程控制协议

### 为什么仍然需要一个共享待处理队列

这点需要特别说清楚，因为它看起来容易和“不要复杂调度器”混淆。

1. 这不是保留 worker 池。
2. 这是为了处理“线程数达到上限时，fork 出来的 child task 只能先暂存”这一事实。
3. 这个队列就是你说的“loop 结束的时候统一看一下队列里面还有几个待处理任务”的那个队列。
4. 它不承担偷取、唤醒、驻留等待等职责，只承担一个功能：在线程数达到上限时临时存放尚未启动的 task。

这里再补一个约束：

5. 为了避免多个线程同时结束时重复补线程，补线程动作会有一个非常薄的互斥拥有者概念：
   - 同一时刻只允许一个线程执行“查看队列积压量并批量 spawn”；
   - 这个拥有者不是中央调度线程，只是某个恰好刚结束 task 的工作线程临时承担一次补线程动作；
   - 补完就退出，不驻留。

更直白地说：

- 原模型是“线程活着就是为了等活、偷活、再干活”。
- 新模型是“线程活着是为了干手上的 path；干完后释放名额，再看公共队列里有没有能立即补开的 task，然后退出”。

### 计划步骤

1. 在 `executor.rs` 内部引入一个很薄的 fork 提交抽象，例如 `ForkSink` / `ForkRuntime`：
   - `start_single` 使用单线程版本；
   - `start_multi` 使用多线程版本；
   - `run_loop(...)` 不再直接依赖 `Worker<Task<_>>`。

2. 修改 `run(...)` / `run_loop(...)` 的内部参数：
   - 将当前用于 fork 的本地队列参数替换为统一的 fork 提交接口；
   - 保持单线程和多线程都复用同一份 `run_loop(...)` 主逻辑。

3. 修改 `run_loop(...)` 中两处 fork 点：
   - 不再直接 `queue.push(Task { ... })`；
   - 改为调用统一的 `submit(task)`；
   - 在 multi 模式下，`submit(task)` 会在 fork 当下直接尝试创建新线程。

4. 重写 `start_multi(...)` 的内部实现，但不改它的函数签名：
   - 不再保留 `Poke` / `Idle` / `Kill` 这套外部调度器；
   - 不再依赖固定 worker 池；
   - 使用 `thread::scope(...)`、线程上限计数、以及一个共享待处理队列来控制线程数量；
   - 初始 tasks 与 fork child tasks 统一走同一套 `submit(task)` 路径。

5. `start_multi(...)` 的多线程提交策略：
   - 若当前活跃线程数小于上限，则在 fork 所在线程中立即 `spawn` 新线程执行 child task；
   - 若当前活跃线程数已到上限，则将 child task 放入共享待处理队列；
   - 线程在完成当前 task 后，释放名额，并尝试取得一次性的补线程执行权；
   - 取得执行权的线程统一检查共享待处理队列里当前积压的任务数；
   - 按当前剩余线程名额一次性批量 `spawn`；
   - 当前线程自己退出，不保留常驻 worker。

6. `start_single(...)` 的处理原则：
   - 保持其对外语义不变；
   - 仅做最小适配；
   - single 模式下的 `submit(task)` 仍然只是把任务放回本地顺序执行容器。

7. 完成后验证：
   - `cargo check -p isla-lib`
   - 确认 `start_single` / `start_multi` 的外部调用点无需修改；
   - 再观察 fork 后的 CPU 利用行为是否更接近“即时并行”；
   - 确认 `start_multi(...)` 中不再存在依赖外部信号唤醒后再创建线程的路径。

## 关键设计取舍

1. 不保留复杂 worker 池：
   - 原因不是 worker 一定错误，而是它不符合本话题对“fork 即时并行”的主要目标。

2. 保留一个最小化的共享待处理队列：
   - 这是在线程数达到上限时保存额外 task 的必要结构；
   - 它不等于固定 worker 池，也不意味着需要额外阻塞调度器；
   - 线程结束后只做“释放名额 + 批量补 spawn”，不做“自己接着跑”。

3. 仍然无法消除首次 fork 前的单路径瓶颈：
   - 如果某段执行在第一次 fork 前本来只有 1 条路径，那么该阶段仍然只能由 1 个执行单元推进；
   - 本次改造解决的是“fork 之后的即时并行”，不是“把单一路径强行拆成多核”。

4. 不保留中心化完成判定调度循环：
   - 线程的收敛由 `thread::scope(...)` 和动态线程自然退出完成；
   - 不再依赖主线程持续接收 `Finished/Idle` 再判断是否 `Kill` worker。

5. 保持 fork 点创建线程，而不是外部收到事件后再创建线程：
   - 这样能严格符合“遇到 fork 时立即尝试并行”的目标；
   - 代价是 fork 热路径要承担少量原子计数与提交逻辑，但这比重新引入外部调度器更贴近本话题诉求。

6. 不采用“线程完成后自己继续串行消费队列”的方式：
   - 这样更符合“线程结束就结束”的偏好；
   - 队列中的任务统一通过新的 `spawn` 获得执行单元，而不是让旧线程继续扮演 worker。

7. 不采用“弹一个 task 就补一个线程”的细粒度补线程方式：
   - 这样会让退出路径承担过多原子争用；
   - 也不符合“第一个出来的线程看到积压任务后尽量一次性补满 CPU”的目标；
   - 因此这里采用“单个拥有者批量补线程”的方式。

## 预期内部结构

为了便于后续实现时对齐，我预期最终内部结构大致如下：

1. 单线程路径
   - `start_single(...)`
   - `SingleForkSink`
   - 本地顺序容器
   - `run(...)` / `run_loop(...)`

2. 多线程路径
   - `start_multi(...)`
   - `MultiForkRuntime`
   - `submit(task)` 负责 inline spawn 或共享队列回退
   - 线程执行函数负责“执行当前 task -> collector -> 释放名额 -> 若拿到补线程执行权则批量补 spawn -> 退出”

3. 共享执行内核
   - `run(...)`
   - `run_loop(...)`
   - 两处 fork 点都改为调用统一提交接口

## 实现注意事项

1. 线程上限控制需要使用原子 compare-and-swap 一类的手段，避免多个线程同时 fork 时超过 `limit`。
2. `thread::scope(...)` 的生命周期会影响内部抽象形状，实现时可能更适合用带生命周期参数的内部结构，而不是过度依赖 trait object。
3. 需要保证每个 task 只被执行一次，不能同时存在于“已 spawn 的线程”和“共享队列”中。
4. 初始 `tasks` 可能多于 `num_threads`，因此初始派发阶段也必须经过同一套限流与共享队列逻辑。
5. 多个线程可能同时结束并尝试“从队列补 spawn”，因此补线程的逻辑也必须受同一个原子线程上限控制，避免重复创建或超过 `limit`。
6. 多个线程可能同时结束，因此需要一个极薄的“补线程执行权”原子标记，保证同一时刻只有一个线程负责批量补线程。
7. 补线程的过程不是“弹一个，抢一个，spawn 一个”的一对一细粒度流程，而是：
   - 先基于当前 `active_threads` 与 `limit` 计算可补线程数；
   - 再查看共享队列中的当前积压任务量；
   - 最后一次性批量 `spawn` `min(积压任务量, 可补线程数)` 个线程。
8. 这里的一次性批量 `spawn` 仍然要受统一线程上限控制，不能因为两个线程同时退出而让系统超出 `limit`；因此“批量”依赖的是独占补线程执行权，而不是无锁地先读长度后盲目创建。
